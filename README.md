# DXT-decoder-bench

Slightly hacky benchmarks over bytedance/sonic, goccy/go-json and json/v2 for the same sample data. I'm benchmarking without using _test.go, no testing.B which disables inlining and some optimisations. Memory counts are read using runtime, which can be off by a few bytes but is more than accurate enough to comment on what is going on in terms of allocations.

I've set on all cores the frequency governor to performance, and disabled low power states. Tests are run on a 13900K in SCHED_FIFO with prio 99.

Because I have some other work I'm doing rn I didn't want to reboot and change my kernel boot settings to have a proper rcu_nocbs isolcpus etc boot with pcie power states and all the fancy serious benchmarking tunings. Instead, I just trimmed the 0.01% tail, which is close enough.

------------

sample.json has 32 book snapshots exported from my S3 at 512KiB or so, we warmup by running over the entire set 50 times. Then we run over the full set 1000 times using rdtsc to time each book decode without too much overhead. 

Test runs are pinned to an OS thread, and that thread is affined to a single core. This just keeps us on a core with a warm cache for the books, which is similar to what I would expect to see if we had streamed the book off of the network and into a buffer to decode.

To be consistent with json/v2, I have configured go-json and sonic to copy strings out of the source buffer rather than referencing the input buffer.

Using pprof, we see samples outside of the runtime, and cumulatively, 25% of time in spent in json/v2's `makeString` and in jsontext's `PeekKind` methods.

Meaningfully, `makeStringArshaler.func2` and `makeArrayArshaler.func3` are cumulatively the vast majroity of runtime at 53.8% and 84.2% cum. These are the closures generated by their parent functions (makeStringArshaler, makeArrayArshaler) for decoding a type seen by reflection. 

In arshal_default.go we can understand what is happening;

```
fncs.unmarshal = func(dec *jsontext.Decoder, va addressableValue, uo *jsonopts.Struct) error {
    if uo.Flags.Has(jsonflags.TagFlags) {
        if uo.Flags.Get(jsonflags.StringTag) && !uo.Flags.Get(jsonflags.ReportErrorsWithLegacySemantics) {
            return newUnmarshalErrorBeforeWithSkipping(dec, t, errInvalidStringTag)
        }
        if uo.Flags.Has(jsonflags.FormatTag) {
            return newInvalidFormatError(dec, t)
        }
    }
    tok, err := dec.ReadToken()
    if err != nil {
        return err
    }
    k := tok.Kind()
    switch k {
    case 'n':
        if !uo.Flags.Get(jsonflags.MergeWithLegacySemantics) {
            va.SetZero()
        }
        return nil
    case '[':
        once.Do(init)
        unmarshal := valFncs.unmarshal
        if uo.Unmarshalers != nil {
            unmarshal, _ = uo.Unmarshalers.(*Unmarshalers).lookup(unmarshal, t.Elem())
        }
        var i int
        var errUnmarshal error
        for dec.PeekKind() != ']' {
            if i >= n {
                if err := dec.SkipValue(); err != nil {
                    return err
                }
                err = errArrayOverflow
                continue
            }
            v := addressableValue{va.Index(i), va.forcedAddr} // indexed array element is addressable if array is addressable
            if !uo.Flags.Get(jsonflags.MergeWithLegacySemantics) {
                v.SetZero()
            }
            if err := unmarshal(dec, v, uo); err != nil {
                if isFatalError(err, uo.Flags) {
                    return err
                }
                errUnmarshal = cmp.Or(errUnmarshal, err)
            }
            i++
        }
        for ; i < n; i++ {
            va.Index(i).SetZero()
            err = errArrayUnderflow
        }
        if _, err := dec.ReadToken(); err != nil {
            return err
        }
        if err != nil && !uo.Flags.Get(jsonflags.UnmarshalArrayFromAnyLength) {
            return newUnmarshalErrorAfter(dec, t, err)
        }
        return errUnmarshal
    }
    return newUnmarshalErrorAfterWithSkipping(dec, t, nil)
}
```

func3 in makeArrayArshaler is the fncs.unmarshal, makeArrayArshaler returns fncs. This generated closure loops PeekKind() which streams out tokens from the decoder. The decoder tracks nesting, position, handles edge cases, does duplicate name detection, grammar validation, and more. json/v2 zeroes the destination when legacy merge semantics are not enabled. 

json/v2 was actually somewhat engineered for this case, there is the ability to implement UnmarshalJSONFrom on hot types, which in this case, a book level would be a perfect fit for. We can borrow most of the structure of the closure from makeArrayArshaler, but because we know our type, we lose the reflection overhead, indirect calls are reduced as instead of closure calls per elements (400 per side) we can make one call per side. I chose to keep copying strings to maintain consistency with the baseline:

I was somewhat surprised to see go-json being equivalent to, if not ever so slightly faster than, sonic. It seems that for these levels which have very short strings (price, qty), that the go compiler is able to write code which is probably slightly better than what sonic's JIT creates. I think that if I had used marketdata for something like DOGE that results may have shown sonic pulling ahead, but I don't price altcoins.

------

This final part is not really relevant to anything except my own data here, I wanted to dig a little on why sonic didn't beat go-json like I had expected it to. On a deeper level, go-json was hitting ~70% Retired against sonic's 62%. This is likely sonic's  _vstring scanner reducing the instruction count. 

My simple bid/ask {price, qty} levels is likely a bit of an ideal case for go-json against sonic here, backend bound is 18.6% on sonic vs 9.8% for go-json. The data is definitely in L1 cache, so this is probably dependent instruction chains. I cba to try and find out when I'm not being paid to.

Something interesting I found as I did end up trying this on book data from gate.io was that sonic suffers a lot when decoding structs which have more keys than what we care about decoding, go-json can end up being twice as fast.
